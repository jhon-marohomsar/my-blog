Shipping Fast Without Breaking Trust: Lessons in Secure Design from an AI-Assisted Student Application

July 2026 • Cybersecurity • Secure Software Design

Introduction

Modern artificial intelligence tools have changed the way software is developed. AI coding assistants can generate APIs, database models, authentication systems, and user interfaces within minutes. For students and developers participating in hackathons, these tools make it possible to transform an idea into a working prototype in only a few days. However, producing functional software is very different from producing secure software. When developers prioritize speed over security, the result may be an application that appears successful but exposes sensitive information to serious risks.

The scenario presented in this case demonstrates exactly this problem. Three university students built a mobile and web platform that helped student organizations manage memberships, collect event fees, and share files. By relying heavily on an AI coding assistant, they completed a working prototype in less than seventy-two hours and even won recognition during a hackathon. Encouraged by the success, student organizations began using the application to manage real operations.

What started as a demonstration quickly became production software that stored hundreds of students' personal information, including names, student numbers, phone numbers, identification cards, payment screenshots, and private conversations. Unfortunately, the developers never changed their mindset from "build a prototype" to "operate a secure production system." This oversight resulted in several critical security weaknesses that violated fundamental Secure Design Principles and placed users' privacy at risk.

What Went Wrong

The application's biggest weakness was that it was treated as a finished product simply because it worked. The developers focused on implementing features quickly, but they did not perform a security review before real users began storing personal information in the system. As more organizations adopted the platform, the amount of sensitive data increased, yet the application's security remained at the same prototype level.

The first major issue involved broken authorization. Users could modify the number at the end of a profile URL and immediately view another student's personal record. This vulnerability is known as an Insecure Direct Object Reference (IDOR). The application checked whether a user was logged in but failed to verify whether the user actually had permission to access the requested resource.

This violated the Secure Design Principle of Complete Mediation. Every request should be validated before access is granted. Authorization is not something that should happen only during login. Each request must confirm that the authenticated user owns or is authorized to access the requested information.

Another serious problem was the exposure of sensitive credentials through the project's public GitHub repository. Database passwords and payment API keys were stored directly in the source code and committed into version control. Anyone viewing the repository could potentially obtain full access to backend services.

This violated the principles of Secure Defaults and Least Privilege. Secrets should never be hardcoded into source code. Instead, credentials should be stored securely using environment variables or a secrets management service. Furthermore, each service should only receive the minimum permissions necessary to perform its specific tasks.

The application also configured every account with broad database read permissions. Instead of restricting users to their own records, database queries could access almost every student's information. This violated the principle of Least Privilege, which states that users, applications, and services should receive only the minimum level of access necessary to complete their responsibilities.

Error handling created another significant security problem. When unexpected errors occurred, the application displayed complete stack traces directly in the browser. These messages exposed internal file names, framework details, and backend implementation information that attackers could use to identify additional vulnerabilities.

Displaying detailed error information violated the principle of Fail Secure. Secure systems should fail safely by providing generic error messages to users while recording detailed information only in protected server logs accessible to administrators.

Communication between users and the server occurred over plain HTTP instead of HTTPS. This meant sensitive data, including login credentials and uploaded identification documents, could potentially be intercepted over unsecured networks.

Operating without encrypted communication violated the principle of Defense in Depth. Security should rely on multiple protective layers, including transport encryption, secure authentication, authorization, logging, monitoring, and network protections.

Finally, the developers believed that hiding the application's internal URLs would discourage attackers. This assumption represented a classic example of security through obscurity.

This violated the principle of Open Design, which emphasizes that systems should remain secure even when their design is publicly known. True security depends on strong access controls, secure authentication, encryption, and proper authorization—not on keeping URLs or implementation details secret.

Secure Design Principles Violated

  • Complete Mediation – Every request should verify authorization before granting access. The application failed to perform ownership checks on profile requests, allowing unauthorized access to student records.
  • Least Privilege – Database users and application accounts received excessive permissions, increasing the impact of any compromise.
  • Secure Defaults – Sensitive credentials were embedded directly into source code instead of secure environment variables.
  • Fail Secure – Stack traces exposed internal implementation details instead of failing safely.
  • Defense in Depth – The application relied on a single layer of protection while lacking HTTPS, monitoring, proper authorization, and secure secret management.
  • Open Design – Developers assumed hidden URLs would protect the application rather than implementing proper security controls.

Short-Term Containment: The First Hours and Days

Once the vulnerabilities were confirmed, the highest priority should be preventing further exposure of students' personal information. The first step would be to immediately take the application offline to stop unauthorized access while an investigation is conducted. This action restores the principle of Fail Secure because the system fails in a way that protects data instead of continuing to expose it.

The next action would be rotating all compromised credentials, including the database password and payment API keys. Since these secrets were publicly available in the GitHub repository, they should be considered compromised even if there is no evidence they were used. New credentials should replace the old ones immediately. This restores the principles of Secure Defaults and Least Privilege.

The development team should also remove secrets from the repository, rewrite Git history if necessary, and move all confidential information into environment variables or a secure secrets manager. Simply deleting the files is not enough because Git preserves previous commits.

Another immediate priority is implementing proper authorization checks. Every request for user profiles, uploaded documents, payment records, and organization files should verify that the authenticated user has permission to access the requested resource. This restores the principle of Complete Mediation.

The application should also disable detailed error messages in production. Users should receive generic messages such as "An unexpected error occurred," while detailed stack traces should only be written to secure server logs for administrators. This restores Fail Secure.

Finally, the development team should notify the faculty adviser and affected student organizations about the incident. Transparency is essential when personal data may have been exposed. System logs should be reviewed to determine whether unauthorized access occurred before the application is restored.

Long-Term Secure Design Improvements

After immediate containment, the focus should shift to rebuilding the application with security integrated into every stage of development rather than added as an afterthought. The first improvement would be adopting Role-Based Access Control (RBAC). Different users such as students, organization officers, and administrators should have clearly defined permissions based on their responsibilities. This reinforces Least Privilege.

Authentication and authorization should be separated. Logging in proves who the user is, while authorization determines what the user is allowed to access. Every API endpoint should verify both identity and permission, ensuring that ownership checks occur on every request. This reinforces Complete Mediation.

All communication between users and the server should be protected using HTTPS with TLS encryption. Encryption safeguards login credentials, uploaded identification cards, payment screenshots, and private conversations from interception. This strengthens Defense in Depth.

Sensitive credentials should never be stored inside the application's source code. Instead, developers should use environment variables or dedicated secrets management tools. Access to production credentials should be limited to authorized personnel only. This restores Secure Defaults and Least Privilege.

The application should also implement secure logging, regular backups, monitoring, and automated alerts. Failed login attempts, unusual account activity, and repeated authorization failures should trigger security notifications so administrators can respond quickly. These measures strengthen Defense in Depth.

Input validation should be implemented on both the client and server. Every uploaded file, form input, and request parameter should be validated to reduce the risk of malicious input and application abuse. This supports Economy of Mechanism by keeping validation simple, consistent, and centralized.

Security should also become part of the software development lifecycle. Code reviews, penetration testing, dependency scanning, and vulnerability assessments should occur before every production release. AI-generated code should never be accepted without careful human review because AI focuses on generating functional solutions rather than guaranteeing secure ones.

Developer Responsibilities Under RA No. 10173

The Philippines' Republic Act No. 10173, also known as the Data Privacy Act of 2012, establishes the responsibility of organizations and developers to protect personal information. The student application stored names, student numbers, phone numbers, identification cards, payment screenshots, and private conversations. All of these are forms of personal information that must be processed responsibly.

As developers, our design decisions directly affect the privacy of every user. Choosing to skip authorization checks, exposing credentials, or ignoring encryption can place hundreds of individuals at unnecessary risk. Secure software design is therefore not simply a technical requirement—it is also an ethical and legal responsibility. Following secure design principles helps developers comply with the objectives of the Data Privacy Act by protecting confidentiality, integrity, and availability of personal data.

Reflection and Conclusion

This scenario demonstrates that software can appear successful while still being dangerously insecure. The application achieved rapid adoption because it solved a real problem for student organizations, but its success also increased the consequences of poor security decisions. Winning a hackathon or delivering features quickly should never be mistaken for producing software that is ready to handle sensitive personal information.

AI coding assistants are valuable tools that can significantly improve developer productivity, generate boilerplate code, and accelerate learning. However, developers remain fully responsible for verifying the security, correctness, and privacy implications of the generated code. AI can suggest implementation details, but it cannot replace careful design, professional code review, or ethical decision-making.

As a future Information Technology professional, this case reminds me that every software project carries a responsibility to protect the people who trust it. Building quickly is important, especially during hackathons and academic projects, but protecting user data is even more important. Secure design should never be viewed as an optional feature added after deployment. Instead, it must be treated as a fundamental requirement from the very beginning of the software development process. By applying Secure Design Principles, performing proper security testing, and respecting the obligations established by RA No. 10173, developers can build systems that earn users' trust while protecting their privacy and personal information.
